# FenxTek Shorthand Classes — multi-page site

Static multi-page website with a student portal and an admin CRM. Pages are plain HTML/CSS/JS; Firebase Authentication + Realtime Database provide sign-in and live content.

## Pages

| File | Purpose |
| --- | --- |
| `index.html` | Home (legacy single-page is still `fenxtek-v2.html`) |
| `courses.html` | Courses: dark hero with a live-dictation console, batch grid from RTDB with tag filter chips, "in every batch" bento, fee cards with save %, admission timeline |
| `exams.html` | Exams: category matrix hero, searchable exam explorer (sticky search + category jump chips), speed ladder, exam-day rules |
| `method.html` | Method: daily-loop orbit hero, three detailed steps with mock UI, sample week, illustrative progress chart, why-FenxTek bento |
| `about.html` | About: director portrait hero, director's note (from RTDB), values, testimonials, explore links, contact cards |
| `achievements.html` | Achievements: dark hero with the latest post as a spotlight, ticker, an uncropped photo wall with tag filters, a full-screen reader (zoom, drag, swipe, download, open original) and a "share your result" section |
| `membership.html` | Membership plans (from RTDB), "your membership" banner for signed-in students, FAQ |
| `contact.html` | Join form and contact details |
| `auth.html` | Student sign in / sign up (email + Google) |
| `dashboard.html` | Student portal app: home, My courses + classroom, Course store, course pages, cart with coupons, checkout, orders and PNG receipts, **membership plans bought through the same cart and checkout**, profile |
| `admin.html` | Admin CRM (content, collections, membership plans, student memberships, achievements, students, leads) plus the **Store**: orders & receipts, courses, coupons, payment settings |
| `forgot.html` / `404.html` | Password reset / not-found page |

### Page map — which page reads which RTDB node

`content.js` reads `<body data-page>` and subscribes only to the nodes that page shows (see `PAGE_MAP` in `assets/js/content.js`):

| Page | RTDB nodes |
| --- | --- |
| Home | `site/content`, `site/testimonials`, `site/achievements` (latest 3) |
| Courses | `site/content`, `site/batches`, `site/fees` |
| Membership | `site/content`, `site/memberships`, `site/faqs`, `members/<uid>` (signed-in only) |
| Achievements | `site/content`, `site/achievements`, `site/achievementImages/<id>` (lazy, per picture) |
| Contact | `site/content`, `site/memberships/<id>` when opened as `contact.html?plan=<id>`; writes `site/leads` |
| About | `site/content`, `site/testimonials` |
| Exams, Method, Auth, Forgot, 404 | `site/content` (footer contact details) |
| Dashboard | `users/<uid>`, `members/<uid>`, `site/content`, `site/courses`, `site/courseImages`, `site/offers`, `site/payments`, `carts/<uid>`, `orders/<uid>`, `enrollments/<uid>`, `courseAccess/<id>` and `courseContent/<id>` (enrolled only), `courseOutline/<id>`, `coursePreview/<id>`, `progress/<uid>`, `coupons/<CODE>` (one code at a time, when typed) |
| Admin | everything (admin only) |

Navigation (header, mobile menu, footer) is generated by `chrome.js`, so a new page only needs adding to its `NAV` list.

Shared code lives in `assets/css/site.css` (design system), `assets/css/portal.css` (portal/CRM), and `assets/js/`.

- `chrome.js` injects the sprite, header, mobile menu, footer and page effects.
- `site.js` handles interactions (preloader, reveals, counters, FAQ, join form, footer wordmark).
- `content.js` mirrors RTDB content onto the public pages, using the page map above.
- `media.js` shared helpers: escaping, image URL / base64 validation, the lazy achievement-image loader and the CRM image compressor.
- `auth-ui.js` updates the header “Portal” link after sign-in.
- `firebase.js` loads the Firebase v10 SDK on demand and wraps auth/database helpers.
- `commerce.js` store logic shared by the portal and the CRM: course normalising, coupon checks, cart pricing, order numbers, UPI links.
- `receipt.js` draws the premium receipt on a `<canvas>` (2× resolution) and downloads it as `FenxTek-Receipt-<order no>.png`.
- `dashboard.js` is the student portal. Routes live in one `ROUTES` registry — a new section (live classes, test series, notes…) is one entry plus one view function; the sidebar, mobile tab bar and title pick it up.
- `admin-store.js` is the CRM's Store section (orders, courses, coupons, payments); `store.css` styles the portal and the store screens.

### From scratch

1. Create a project at <https://console.firebase.google.com>.
2. Add a **Web app** and copy the config object.
3. **Authentication → Sign-in method**: enable **Email/Password** and **Google**.
4. **Build → Realtime Database**: create a database (start in locked mode).
5. Paste your values into `assets/js/firebase-config.js`:

```js
export const firebaseConfig = {
  apiKey: "…",
  authDomain: "your-project.firebaseapp.com",
  databaseURL: "https://your-project-default-rtdb.firebaseio.com",
  projectId: "your-project",
  storageBucket: "your-project.appspot.com",
  messagingSenderId: "…",
  appId: "…"
};

export const ADMIN_EMAILS = ["your-admin@gmail.com"];
```

6. Open `database.rules.json` and replace the admin email in the `admins` rule with the same address. In the Firebase console go to **Realtime Database → Rules**, paste the file contents and publish.
7. **Authentication → Settings → Authorized domains**: add `localhost` (already default) and your production domain.

> The config values are not secrets; the database rules are what protect the data. Never commit a service-account key.

- Public read access: `site/content`, `site/batches`, `site/fees`, `site/faqs`, `site/testimonials`,
  `site/memberships`, `site/achievements`, `site/achievementImages`.
- `members/<uid>`: each student can read their own record. Admins can write it, and a student can write it
  only in the same update as a **paid** order of theirs that contains that plan (see *Membership purchase* below).
- Achievement pictures are stored separately from the post text so list pages stay light and each
  base64 image is downloaded only when it scrolls into view. The rules cap one picture at ~1.5 MB of
  base64. The CRM keeps them readable: up to ~4.2 MP with a 3600 px long side (tall result lists keep their full width), PNG for screenshots when it fits, JPEG 0.92→0.76 otherwise, always flattened onto white so transparent screenshots don't turn into dark-on-dark text, and capped at ~1.15 MB of base64 (the rules allow < 1.5 MB).
- Public write access: create-only on `site/leads` (email validated by the rules).
- `users/<uid>` is readable/writable by that user; admins can read all students.
- Store: `site/courses`, `site/courseImages`, `site/offers` and `site/payments` are public. Signed-in students
  read and write their own `carts/<uid>`, read their own `orders` / `enrollments`, and can read a single
  `coupons/<CODE>` they type (the coupon list itself is admin-only, so codes can't be harvested).
- The rules check every student checkout: item prices and validity must equal the live course, the total must be
  `subtotal − discount`, the coupon must exist, be active, in date and under its use limit, and `couponUsage`
  must go up by exactly one in the same write. Students can only create three kinds of order: **pending UPI**
  with a UTR, **paid Razorpay** with a `pay_…` id, or **free** (₹0 because of a coupon). Enrolments must point
  at a paid order of theirs and can't run longer than the course validity.
- Free (₹0) orders are only accepted when the coupon really covers the whole cart: a 100% coupon with no cap
  (or a cap ≥ subtotal), or a flat coupon worth at least the subtotal, and every item must be in the coupon's
  scope. No item may cost more than the order subtotal, so the subtotal can't be under-reported.

### Membership purchase

Membership plans are sold exactly like courses: **Buy membership** (or the cart icon) on a plan puts
`plan_<planId>` into the student's cart, next to any courses. Coupons, offer tiles, UPI with UTR, Razorpay, ₹0
coupon orders, receipts and the admin Orders screen all work the same way. One plan per order: adding a
second plan replaces the first.

- The order item copies the plan's price, struck-through price and `durationDays`. The rules compare them with
  `site/memberships/<planId>` and reject hidden plans. The portal only offers *Buy* on plans that have a price
  and a length in days.
- **Paid right away** (Razorpay or a ₹0 coupon): the same multi-path update writes the order, the coupon usage and
  `members/<uid>`. The rules accept the membership only if it points at that paid order (`orderId`,
  `orderPaidAt` = the order's `paidAt`) and the dates match the plan: `startAt` = paid time, and `endAt` no later
  than paid time + plan days. Buying the **same** plan again while it is still active **extends** it from the current
  end date and keeps the original start date. Buying a different plan switches to it from today. Re-using an older
  order is rejected because `orderPaidAt` must be newer than the record being replaced.
- **UPI:** the order stays *pending*. When an admin clicks **Approve** in Store → Orders, the membership
  is activated, with the same extension logic. **Refund / reject** cancels the membership if it came from that order.
- **Record offline sale** and the coupon scope picker list plans next to courses (coupons can target only certain
  plans, e.g. a `MEMBER20` offer).
- Deep links: `dashboard.html#membership` (plans + "your membership" card), `dashboard.html#membership/<planId>`
  (scrolls to the plan), and `dashboard.html#join/<planId>`, which adds the plan to the cart and opens the cart. The public
  `membership.html` buttons use `#join/<id>`, so a signed-out visitor goes through sign-in and lands in the cart.
  Plans without a price still link to `contact.html?plan=<id>`.
- Purchase buttons: every plan card on `membership.html` has a **Buy now** button showing the plan's price and
  validity, plus *Secure checkout · Instant activation · Receipt* and a "Questions? Talk to us" link. Signed-in members
  see **Extend plan** on their own plan and **Switch to this plan** on the others. The signed-in banner above the cards
  offers **Buy <plan>**, **Extend plan** or **Renew plan**, and the membership promo on the portal's Home and Store
  has a direct **Buy <plan>** button next to *View plans*. A custom CTA text set in the CRM replaces "Buy now".
- Plan prices: the CRM saves `price` / `was` as numbers. Plans saved by an older version may hold text such as
  `"749"`. The rules accept both, but open **Memberships** in the CRM and click **Save** once on each plan to store numbers.
- Everything else requires an admin entry under `admins/`.

### Course content (classroom)

**Adding content (Store → Courses → Content).** Each course row has a **Content** button and an
"N folders · N items" pill. It opens a full-screen manager:
- **New folder** creates folders, and folders can sit inside folders (chapters → topics). Click a folder to open it,
  and use the breadcrumb to go back.
- **Add content** takes any link. Paste it and the type is detected for you: YouTube (videos, playlists, Shorts,
  live), Vimeo, Google Drive files and folders, Docs, Sheets, Slides, PDFs, mp3/mp4, Zoom, Meet, Telegram, Dropbox
  and any webpage. The title fills in from the link. You can set the folder, duration, the date and time of a live
  class, a description, **Free preview** (visible to everyone on the course page) and **Hidden** (a draft that
  students can't see).
- **Bulk add** takes one link per line, as `Title | https://…`, `Title https://…` or just the link.
- Each row can move up or down, open the link, hide or show, be edited, or be deleted. Deleting a folder deletes
  everything inside it.
- Every save also rewrites `courseOutline/<id>` and `coursePreview/<id>` in the same update, so the public syllabus
  never shows drafts or private links. **Preview as student** opens the classroom in a new tab. Admins can always
  open it, and the header is labelled *Admin preview*.
- Drive and Docs files must be shared as "Anyone with the link".

**What students see.** Under *My courses* → **Continue learning** (`dashboard.html#learn/<courseId>`):
- **Classroom:** progress ring, **Continue** (or **Start learning**), the notice board from **Classroom links**,
  folder cards with per-folder progress, a search box and type chips (Videos, PDFs, Audio…). Each item shows
  ✓ done, *New* (first 7 days) and its source.
- **Viewer** (`#learn/<courseId>/i/<itemId>`): YouTube, Vimeo, Drive, Docs and PDFs play inside the portal. PDFs
  open through Google's viewer, with a link to the original file. mp4 and mp3 files play natively, and images show
  inline. Live classes show a **Join live class** card (*Upcoming / Live now / Ended*). Other links open in a new
  tab. You also get **Mark as complete**, Previous / Next and an "In this folder" playlist.
- **Progress:** notes, files and links count as done once opened. Video and audio count when they finish or when
  ticked, and live classes when joined. Progress is saved in `progress/<uid>`, and the *My courses* card shows
  "N% complete".
- **Not enrolled or expired:** the course page shows a **Curriculum** panel with folder counts and a free-preview
  strip. The classroom shows the outline with locks. Locked items show **Enrol to unlock**, and free previews play.

### Gifted memberships: by email or by QR code

**By email (Memberships → Student memberships).** Type the student's email (accounts are suggested as you type).
- The email belongs to a student account → the plan is written to `members/<uid>` straight away (`source: "admin"`).
- No account yet → it is saved as an **invite** under `memberInvites/<email key>` and shows as *Invite pending* in the
  table (edit or cancel it there). The first time that person opens the portal with a **verified** email, the portal
  activates the plan and deletes the invite in one update. "Valid till" becomes a number of days counted from that
  moment. Google sign-ins are already verified; email/password students see a banner with **Send verification
  email** and **I've verified**. The rules only release an invite to the matching, verified email address.

**By QR code (Memberships → Membership QR codes).** Pick a plan; a code such as `QUARTERLY-7KQ2XM` is generated
(edit it if you like). Set validity in days (blank = the plan's length, 0 = open-ended), max students (blank =
unlimited), an optional expiry date and a private label. Each code card shows its QR, uses (`3 / 50 joined`), and
**Show QR** (big QR, link and the list of students who joined), **Poster** (downloads a 1080×1350 PNG to print or post
in WhatsApp groups), **Copy link**, **Pause/Resume** and delete.
- The QR opens `dashboard.html#redeem/<CODE>`. Signed-out students sign in first and come straight back. Students
  can also type the code in **Have a membership code?** on the portal's Membership page.
- The redeem screen shows the plan card, validity and what will happen (adds days to the same plan, or replaces a
  different one), then **Activate membership**.
- One update writes `members/<uid>` (`source: "code"`, `code`), bumps `memberCodeUsage/<CODE>/count` by exactly
  one and records the student under `users/<uid>`. The rules reject paused, expired, full or unknown codes, a second
  use by the same student, back-dated starts and longer validity than the code gives.
- Same plan still active → the days are added to the current end date (start date kept), exactly like a renewal.
- QR codes are drawn by a vendored copy of `qrcode-generator` 1.4.4 (MIT) in `assets/vendor/`, via `assets/js/qr.js`.

### Member pricing and member-only coupons

**Extra member discount on courses.** Each membership plan has **Member discount on courses (%)** (Memberships →
plan editor, 0–90, saved as `site/memberships/<plan>/courseOff`). A student with an active plan pays that much less
on every course. To fix an exact price for a course, set **Member price** on the course (Courses → `memberPrice`); the
lower of the two wins. Non-members see "Members pay ₹X" on store cards and course pages, and the cart shows how much
they would save with a membership. Orders store `memberDiscount` and `memberPlan`. Receipts, the orders table and
the CSV export show it as its own line.

**Member-only coupons.** Coupons → **Who can use it**: *Everyone*, *Members only* or *Members of selected plans*
(saved as `coupons/<CODE>/members: true` plus an optional `memberPlans: { planId: true }`). A member-only coupon is
applied after the member price. Non-members see it locked in the cart with a **Join** link. The rules check the
student's `members/<uid>` record (active, not expired, right plan) when the order is created, so it can't be bypassed.

### Refer & earn (E-coins)

Admin → **Refer & earn** controls `site/rewards`: on/off, coins for the referrer, coins for the new student, the
maximum % of an order payable with coins, and an optional minimum first order. **1 E-coin = ₹1.**

- Every student gets a code (`users/<uid>/refCode`, reserved in `refCodes/<CODE>`) and an invite link
  `dashboard.html#ref/<CODE>` on the portal's **Refer & earn** page (WhatsApp, Telegram and copy).
- A new student who opens the link (or enters the code) before their first order is linked in
  `referrals/<uid>` and `referredBy/<referrer>/<uid>` as *pending*.
- When that student's first paid order is confirmed (UPI approved, Razorpay verified or an offline sale), both wallets
  are credited in the same update and the referral turns *rewarded*. Free (100% coupon) orders never qualify.
- At checkout students turn **Use E-coins** on and off. Coins are capped at the configured % of the payable amount,
  and at least ₹1 is always paid by UPI or Razorpay. The order (`coins`), the wallet debit (`wallets/<uid>`) and the
  history entry (`walletTx/<uid>/<orderId>`) are written together. The rules make sure the balance only goes down
  by exactly the order's coins.
- Rejecting or refunding an order returns the coins. Refunding a referral-qualifying order asks whether to take
  back the referral coins too.
- Admins can see every referral and wallet, add or remove coins manually (with a note), and open any student's coin
  history.

## Using the CRM

Open `admin.html` and sign in with the admin account.

- **Overview** — live counts, current price, published announcement.
- **Site content** — hero paragraph, counters, starting price, phone/email/social handles, director details and the student-dashboard announcement.
- **Batches / Fees / FAQs / Testimonials** — add, edit, reorder or remove rows, then **Save**. Public pages re-render from RTDB immediately (no rebuild).
- **Memberships** — **Create plan** adds a plan card to the Membership page (name, price, struck-through price, validity label and days, one feature per line, highlight badge, **card style**, visible on site). Each plan shows as a premium membership card: *Midnight black*, *Royal violet*, *Champagne gold* or *Pearl white*. Leave the style on **Auto** and the highlighted plan becomes the Midnight card with the animated border, while the others cycle violet → gold → pearl. The page works out "Save X%" from the struck-through price and "≈ ₹N a day" from the validity in days, and the hero shows up to three plan cards fanned out, highlighted plan in front. Below that, **Student memberships** gives a plan by email: type the student's email and pick a plan, and "Valid till" fills in from the plan length. Emails without an account become invites that activate on first sign-in. **Membership QR codes** creates scan-to-join codes with posters (see *Gifted memberships* above). Students see it on their dashboard and the Membership page. The Students tab has an **Assign plan** shortcut too.
- **Achievements** — drag & drop a photo onto the drop zone (or click to browse, or paste with Ctrl/⌘ + V), or switch to **Picture link** and paste an `https://` image URL (Google Drive / Dropbox / GitHub share links are converted to direct picture links; Drive files must be shared as "Anyone with the link"). Add a caption (required), optional title, tag and date, then **Publish post**. Uploaded photos are saved in RTDB as base64; links are saved as-is. Posts can be edited, hidden, reordered with the arrows, or deleted. `admin.html#achievements` opens the tab directly. If the live database blocks anonymous reads, the tab shows a red **Visitors can't see these posts yet** warning (it checks with an unauthenticated REST request), which means `database.rules.json` still needs publishing.
- **Students** — accounts created through the portal.
- **Store → Orders & receipts** — every checkout with revenue stats, search (order no, student, phone, UTR, payment id, coupon) and filters. **Approve** a UPI order once the UTR shows in your bank app — this enrols the student (or activates their membership). Razorpay orders show **Verify** until you tick them off against the Razorpay dashboard. View or download any receipt as PNG, reject / refund (removes access), **Record offline sale** for cash or bank transfers, and **Export CSV**.
- **Store → Courses** — create and edit the courses sold in the portal: price, struck-through MRP, validity (or lifetime), category, mode, language, badge, features, description, cover colour or uploaded cover, publish / hide, reorder. **Content** opens the content manager: folders, videos, PDFs, notes, webpages, audio and live classes (see *Course content* above). The link icon (**Notice & class links**) sets the notice board message and standing links (Telegram group, Zoom room…) shown at the top of the classroom. **Import from batches** turns the existing batch list into draft courses.
- **Store → Coupons** — a single code or **Bulk generate** up to 500 unique codes per run (run it as often as you like). Each coupon is **percent** (with an optional ₹ cap) or **flat ₹** off, for everything or particular courses and membership plans, with optional minimum cart value, total-use limit (0 = unlimited), start and expiry dates. Every student can redeem a code once; set total uses to 1 for single-use codes. Tick **Show as offer** to advertise a code in the portal. Filter by batch, pause or delete a whole batch, and export codes with their usage to CSV.
- **Store → Payment settings** — UPI ID and payee name (the portal shows a QR and an "Open UPI app" button and asks for the UTR), the Razorpay key id, and the business name, address, GSTIN, phone and note printed on receipts. **Preview receipt** draws a sample.
- **Leads** — emails captured by the public “Join now” forms, with CSV export and delete. Leads that came through a plan's **Choose plan** button (`contact.html?plan=<id>`) record which plan.
- **Load starter content** — writes the default website content (from `assets/js/cms-defaults.js`) to RTDB, including one starter membership plan. It never touches achievements, student memberships, students or leads.

> **After pulling this update, republish `database.rules.json`** (Realtime Database → Rules). Until you do,
> the live database denies reads on `courseContent`, `courseOutline`, `coursePreview`, `progress`, `site/memberships`, `site/achievements`, `site/achievementImages` and
> `members`, so the Membership page shows its static plan and the Achievements page stays empty — and the
> course store, carts, coupons and orders don't work at all.

> **Payments note.** This is a static site without a server, so a Razorpay payment is recorded with its
> `pay_…` id but isn't verified by a server signature check — that's why Razorpay orders carry a **Verify**
> button in the CRM. For automatic verification, add a small Cloud Function (Razorpay webhook →
> `orders/<uid>/<id>/verified = true`). UPI orders are always manual: the student submits the UTR and you approve.

If a node is missing, the public pages fall back to the HTML that shipped with the site, so a half-filled database never leaves blank sections.
